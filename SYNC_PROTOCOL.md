# storm.dance Sync Protocol

storm.dance uses XMTP as an encrypted group transport and Yjs as the source of
truth for merge semantics. IndexedDB in the browser and `.stormdance/state.bin`
in a linked directory are durable replicas of the same Yjs document.

## Identity and group binding

- One notebook maps to one XMTP MLS group in one XMTP environment. Binding the
  same local notebook in both development and production is rejected because
  its materialized IndexedDB rows are shared.
- The real XMTP conversation ID and environment are stored on the notebook and
  in CLI link configuration; synthetic topics and one-DM-per-peer fan-out are
  not used.
- A group belongs to a notebook only when its description is
  `storm.dance/yjs/1/<URI-encoded notebook ID>`.
- New browser-created groups use admin-only membership and metadata permissions.
- Group membership controls who can receive protocol messages. XMTP provides
  transport encryption; storm.dance does not add a second application-level
  encryption layer to Yjs payloads.

## Yjs document

Each notebook has one `Y.Doc` containing:

- notebook ID, name, creation time, and update time;
- a map of notes keyed by stable note ID;
- `Y.Text` values for note title and content;
- scalar folder ID and timestamps; and
- deletion tombstones, so an offline edit cannot silently resurrect a deleted
  note.

Typing applies a minimal prefix/suffix splice to `Y.Text`. Yjs updates are
commutative, associative, and idempotent, so duplicate, delayed, and reordered
XMTP delivery converges without a last-writer-wins note overwrite.

## Wire messages

Protocol messages are UTF-8 text beginning with `stormdance-sync/1\n`, followed
by strict JSON. Four logical message kinds are supported:

| Kind | Purpose |
| --- | --- |
| `manifest` | Announces notebook identity and schema. |
| `snapshot` | Bootstraps a new group member with the current Yjs state. |
| `sync-request` | Sends a Yjs state vector and asks peers for missing structs. |
| `update` | Carries an incremental Yjs update or a targeted sync response. |

Binary Yjs data is base64 encoded and split into bounded chunks. Reassembly is
strict, duplicate-tolerant, order-independent, TTL-bounded, and capped at 32 MiB
per logical payload. Messages are rejected unless their notebook ID, group ID,
target inbox, schema, chunk metadata, and payload bounds are valid.

## Catch-up and live delivery

On startup, a replica:

1. loads its durable local Yjs state;
2. starts a live group message stream, closing the history/live race window;
3. synchronizes the XMTP group and replays up to 2,048 recent messages;
4. sends a state-vector request;
5. applies the responder's missing update; and
6. returns any update the responder is missing.

The two-way state-vector exchange repairs gaps that fall outside the bounded
history replay as long as another durable replica still has the missing Yjs
state. Local updates are merged and sent after a 250 ms batch window. Failed
sends remain queued for retry, while a later state-vector handshake is the final
recovery mechanism.

Browser Yjs state is keyed by notebook and XMTP environment for explicit
migration safety, while each notebook is allowed one active environment. A
persisted state is authoritative and is materialized before history or live
messages are applied, preventing a stale IndexedDB projection from being
reintroduced as a new edit.

Self-message filtering is based on protocol message IDs generated by the local
installation, not inbox ID. That lets two devices using the same XMTP identity
still synchronize with each other.

## Markdown directory mirror

The XMTP-capable Node 22 CLI and the Rust/Tauri vault bridge share mirror schema
2. One linked vault contains:

- nested, collision-safe `.md` files whose existing paths remain stable when a
  title changes;
- an HTML identity comment, placed after YAML frontmatter when present, carrying
  stable notebook/note IDs, folder ID, and timestamps;
- `.stormdance/config.json` with notebook, conversation, environment, profile,
  and expected-inbox binding;
- `.stormdance/state.bin`, a Yjs-v1 update accepted by both Yjs and Yrs; and
- `.stormdance/manifest.json`, mapping note IDs to owned relative paths/hashes
  and folder IDs to Obsidian directories.

Schema-1 flat vaults are read and upgraded in place. Metadata-free Markdown is
adopted at its existing path, including nested files. YAML frontmatter,
wikilinks, embeds, and fenced code remain note content. Files not owned by the
manifest are never deleted. Both mirrors revalidate exact path-and-hash scan
witnesses before acknowledging a save. The Rust/Tauri mirror retains ambiguous
remote/local replacements as named conflict files; the Node mirror protects the
newer file in place for a later scan. Hidden directories, symlinks, path
traversal, invalid UTF-8, malformed metadata, and unsafe manifest parents are
ignored, protected, or rejected. Writes use same-directory temporary files,
flushes, and atomic rename.

Any Markdown indexer, embedding pipeline, or vector database can consume this
vault without understanding storm.dance. Folder IDs round-trip, and directories
created outside storm.dance receive stable `obsidian:path:<relative path>` IDs.
The browser does not yet synchronize folder entities/names, so a replica that
does not recognize a folder ID shows that note at the notebook root.

## Runtime boundaries

- Hosted web uses Yjs, IndexedDB, and `@xmtp/browser-sdk` directly.
- Tauri hosts the same XMTP/Yjs frontend session and exchanges bounded complete
  Yjs-v1 recovery states with the Rust/Yrs vault watcher through typed IPC;
  native-originated changes enter the frontend as local CRDT updates.
- The packaged Node CLI is the live headless XMTP directory client.
- The packaged Rust CLI currently reconciles local Markdown/Yrs state only and
  reports `networkSynchronized: false`; `storm-xmtp` provides the tested native
  transport boundary, but the pinned direct libxmtp driver is not shipped yet.

## Compatibility

- Browser transport: `@xmtp/browser-sdk` 5.x.
- CLI transport: `@xmtp/node-sdk` 6.x and Node.js 22 or newer.
- Yjs document schema: 1.
- Wire protocol version: 1.
- Markdown mirror schema: 2 (schema 1 is accepted for migration).

Unknown protocol versions are ignored rather than guessed. A schema change must
preserve stable notebook/note IDs and include an explicit migration path.
